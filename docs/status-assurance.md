# Assurance goals 

The assurances Synthyrion Core L5 sets out to achieve, what is achieved so far, what is not, and how strong the checking behind each one is. “Proven” is a word with a size: every claim carries one of four labels, from weakest to strongest. 

**Status.** Synthyrion Core L5 is a capability-based microkernel written in Rust. Its primary target is x86-64. AArch32, AArch64 and RISC-V 64 ports run in emulation (QEMU) only. It is under active development. Its feature status is published on this site, with the strength of each piece of evidence (tested / bounded / panic-free / functionally proven; host, virtual machine or hardware). **It has no safety, security or government certification. There is no whole-kernel functional-correctness proof. It is not FIPS 140-3 validated.** 

**Functional correctness has not been proven.** There is no machine-checked proof that Synthyrion Core L5’s code matches a specification. Everything below is weaker than that, and is labelled with how much weaker. 

## §1The four strengths 
- tested

A property checked on examples. A sample, not a proof. The kernel test suite is the evidence.249 pass
- bounded

Checked exhaustively over every case up to a stated size, comparing the real kernel to a model. A proof about that finite domain only.13 checks
- panic-free

Shown for all inputs that named code cannot panic. Says nothing about whether it does the right thing. Scope: V-548 9 of 10 functions, V-552 the 4 loops by induction, V-553 `synthyrion_caps` 29 of 29.3 proofs
- functionally proven

A machine-checked proof, for all inputs, that the code does what its specification says.0 proofs 

Counts are read from the project’s equivalence table, measured 2026-10-21. A bounded check is a proof about a finite domain only: a property true for three objects can fail at four. The first-party checker that runs these checks is not itself verified. 

## §2The eight assurance goals 

Each is a goal Synthyrion Core L5 sets itself. The status and the strength are read from the project’s own table, measured 2026-11-04; they change when the table changes. The eight assurance goals         

| ID | Goal | Status | Strength today | Achieved | Not yet achieved |
|---|---|---|---|---|---|
| S1 | Abstract specification A complete, machine-checked specification of what the kernel is allowed to do, written in a theorem prover, against which the code can be checked. | In progressstrength: a prover-checked SPECIFICATION of a slice of the kernel; no refinement from the code | no row at the functionally-proven level (the code is not refined to the spec) | An abstract specification of the kernel's own objects exists in the Isabelle prover: the kernel state, capabilities and their derivation tree, retype, the scheduler and a 14-operation invocation layer. Proved on it: the capability and IPC invariants, integrity, and non-interference. | The Rust code is not proved to refine the specification, and some objects are left out of it: mapping and address spaces, call and reply, and parts of fault, interrupt and virtual-CPU handling. |
| S2 | Executable specification A precise model of the kernel that can be run, tied to the real code by exhaustive checks, so that any difference between them shows up as a failure. | In progress | bounded | Executable models of four kernel subsystems are tied to the real kernel code by five bounded exhaustive checks, to depths of 4 to 8. | There is no model of the whole kernel, and a bounded check speaks only for the sizes it names. |
| S3 | Functional-correctness refinement to the implementation A proof, for all inputs, that the kernel's code does exactly what the specification says. | In progress | bounded | The real kernel is checked against the models by forward simulation over finite domains: every case up to a stated size. These checks have found eight defects. | No proof for all inputs exists. A bounded check is a proof about its domain only: a property true for three objects can fail at four. |
| S4 | Binary / translation validation A check that the machine code the compiler produces does what the source says, so that the compiler does not have to be trusted. | In progressstrength: BOUNDED where loops are unrolled, otherwise per function; 2 of 276 kernel functions; NOT a whole-frozen-object result | bounded where loops are unrolled, otherwise per function (2 of 276; not a whole-object result) | An experimental tool checks single compiled x86-64 functions against their source form, with two independent solvers required to agree. When last measured it validated 2 of the kernel's 276 functions. The Rust compiler and its code generator remain trusted. | 274 of the 276 kernel functions have no binary validation, and the result is per function, not for the whole compiled kernel. |
| S5 | Integrity A theorem that no task can change anything it holds no authority over. | In progress | bounded | The enforcement points are checked exhaustively over finite domains: no message is delivered without a live capability that grants write, and the consent and revocation rules hold in every case up to the stated size. | There is no theorem about the whole policy graph, and the exhaustive checks go to three tasks only. |
| S6 | Confidentiality / non-interference A theorem that what one domain does cannot be observed by a domain it is meant to be isolated from. | In progress | bounded at code level (scheduler only) | A machine-checked proof, in the Isabelle prover, of non-interference for an abstract model of the kernel that covers ticks, scheduling, signals, send, receive, wait, copy and mint, move, delete, revoke and retype. An exhaustive check over a bounded domain shows that the real scheduler's choices do not leak between isolated partitions; deliberately leaky schedulers are refuted. | The Isabelle proof is about the abstract model, not the code. The exhaustive check covers the scheduler only: nothing yet for message passing, memory or capabilities in the code. There is no model of deliberate declassification. Timing channels below the architecture are a separate, measured claim. |
| S7 | capDL system-initialisation proof A proof that the system starts in exactly the configuration its description says, with no authority that was not meant to be there. | In progress | tested (fixtures only) | A description language and a checker for the initial system configuration. It refuses configurations that grant forbidden authority, checks the exact build, and convicts planted widened, extra-capability and leaking configurations. It is tested on fixtures. | It has not been run on the real boot distribution, and there is no verified initialiser. |
| S8 | WCET Published upper bounds on how long kernel operations can take, so that real-time deadlines can be shown to be met. | In progress | tested (measured only) | A first-party static analyser computes worst-case bounds. One kernel function is bounded in processor cycles under stated assumptions, and kernel running times are measured. | Bounds for the kernel's entry points are pending, with the reason named for each. Outside timing-analysis tools are planned, not run. |
 

## §3Stricter goals 

These go beyond the eight above. Where rows of the project’s table back a goal, its status is read from them; the others are stated with what is and is not done. Synthyrion's stricter goals        

| ID | Goal | Status | Strength today | Achieved | Not yet achieved |
|---|---|---|---|---|---|
| G1 | Post-quantum cryptography only, with keys of at least 512 bits Every symmetric key is at least 512 bits, key exchange and signatures are post-quantum with no hybrids, and hashes are SHA-512 or stronger. | In progress | tested | Key exchange (ML-KEM-1024), signatures (ML-DSA-87) and SHA-512 hashing are implemented in first-party Rust at the highest standard parameter sets, together with a first-party authenticated cipher with a 512-bit key built on the Keccak permutation (not a NIST-approved algorithm, because no standard cipher has a 512-bit key). Key exchange and authentication between Synthyrion components are post-quantum only, with no hybrid mode. | ChaCha20, whose key is 256 bits, remains in two internal components (key storage and measured boot) and is to be migrated; re-encrypting existing stored keys is a deliberate step, done with backups. None of this is FIPS 140-3 validated. |
| G2 | No third-party code in the kernel Every crate the kernel is built from is written in-house; third-party software runs only in applications above the operating system. | Done | measured | The kernel is written entirely in Rust by the project, and the list of crates it is built from contains only the project's own crates. The list is checked by a test of this site's build, which fails if a third-party dependency appears. | This is a statement about the source. The Rust compiler and its code generator are third-party tools and are trusted until the binary-level check (S4) exists. |
| G3 | Panic-freedom proofs for kernel code A machine-checked proof, for all inputs, that named kernel code cannot panic. | In progress | panic-free | 3 panic-freedom proofs exist, produced by the project’s own first-party checker. Scope: V-548 9 of 10 functions, V-552 the 4 loops by induction, V-553 `synthyrion_caps` 29 of 29. | A panic-freedom proof says nothing about whether the code does the right thing. The checker is itself not verified, and part of the kernel is not yet covered. |
| G4 | A bound on the running time of every kernel entry point A proven worst-case time, in processor cycles, for every call into the kernel. | In progress | tested (measured only) | A first-party static analyser computes worst-case bounds and refuses code it cannot bound (an undeclared loop, an uncosted callee, recursion). One kernel function is bounded in processor cycles on the compiled code, under stated assumptions. | Most kernel entry points are not yet bounded; for each, the blocker is named in the project's generated timing table. The cycle bounds cover Intel cores only, and no interference between cores is proven. |
| G5 | A kernel that detects and repairs damage to itself Bit flips and tampering in the kernel's own tables and image are detected, repaired when a copy can be proven right, and contained when not. | In progress | tested | Page tables and capability tables carry check words; a flipped bit is detected on read and by a background scrubber, repaired in place when one copy can be proven right, and contained when not. Planted flips are caught in tests. A position-independent early-boot image picks a different load address on each boot and refuses an image with a flipped bit; this runs in an emulator. | The check words catch accidents, not deliberate tampering. Object headers, the kernel heap and code, and the hardware copy of the page tables are not covered. The later stages of the plan, several copies that vote and replace a damaged one, are not built. |
| G6 | Every proof and check shown able to fail Each proof or check is accompanied by a deliberately planted fault that it catches, so that a check that cannot fail is not counted as evidence. | In progress | tested | New proofs and checks are submitted with planted faults that make them fail, removed afterwards. Many of the existing ones carry such plants, for example the isolation checks refuse deliberately leaky schedulers, and the self-repair checks catch thousands of planted bit flips. | The rule is applied check by check. Checks that turned out unable to fail have been found and repaired, and the search for more continues. |
| G7 | Runs on x86-64, AArch64 and RISC-V 64, as a guest and as a host, on real multi-core hardware The same kernel on three processor families, with virtualization, and proven on real hardware rather than only in an emulator. | In progress | per row: host, virtual machine or hardware, as labelled on the platforms page | - [x86-64] - [AArch64] (QEMU EL1/EL2 + NAS user-space logic on silicon) - [AArch32] - [Virtualization: virtual CPU object] - [Virtualization: second-level page tables] (ARM at VM strength, no ARM silicon; x86 as stated) - [Virtualization: virtual interrupts] (ARM at VM strength, no ARM silicon; x86 as stated) - [Multi-core, proven on real hardware] - [As a guest on Linux hosts] | - [RISC-V 64] — in progress (QEMU only) - [As a guest on Windows hosts] — in progress - [Hosting a Linux guest] — in progress - [Hosting a Windows guest] — planned |
 

## §4How to read these goals  
- A goal that is not achieved is not described as achieved. The status of each of the eight assurance goals is copied from the project’s own table by the program that generates this page; it is not edited by hand, so it cannot run ahead of the work. 
- Rust’s type system removes whole classes of memory errors, and panic-freedom proofs cover parts of the capability code. Neither is a statement that the kernel does what its specification says. 
- The Rust compiler and its code generator are in the trusted base until goal S4 is achieved.  

When a functional-correctness proof exists, this page will say so, with its scope, and the status of goal S3 will change by itself.
